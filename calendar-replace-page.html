Replace page

Why the current button feels broken, and two proposed flows. Click Replace inside the panel to walk each one. The real wait is 20 to 40 seconds; here it is about 3.

What the team is hitting

Six things wrong with the shipped flow

  1. The replacement looks like it did not take, then gets undone. The panel's fields only reload when you switch items or when the meta description changes. A normal Replace keeps the meta, so the Title and Strategic Angle boxes keep showing the old page. The next keystroke anywhere in the panel autosaves the old title back over the new one. This is the "it doesn't work" report.
  2. Ticking "also regenerate the meta" hides the result. That is the one case where the fields do reload, but the same trigger also resets the Replace section, so it snaps back to the plain link: no before and after, no Undo.
  3. Undo is fragile. The before-snapshot lives only in the panel's memory. Switching items or refreshing loses it for good. Nothing is stored on the server.
  4. A 20 to 40 second wait with a fake percentage, at the bottom of a scrolling panel. The bar is a timer, not progress. When the request runs long the proxy can give up first: you see a red "Request failed" while the backend still saves the replacement, and the item changes on your next reload.
  5. It is discoverable only as 12px text under Strategy Notes, and it stays clickable when the calendar is locked for review or on a sample project, where Undo then fails with a permissions error.
  6. If the AI returns the same title, the section drops back to the empty form as if nothing happened.

The proposal

What both variants share

  • Replace becomes a real button in the panel header. It is hidden when the calendar is locked or the project is a sample, and the backend refuses it in those states too.
  • The flow runs in a card at the top of the panel, under the Google preview, where the eye already is. The bottom section goes away.
  • Reason is a click, not an essay: pick a reason chip, add optional direction. The reason is still logged on the item.
  • Progress is honest: the five real backend steps streamed as they happen, plus elapsed time, no percentage. Fields lock while it runs so nothing you type is lost.
  • The job belongs to the item, not the panel. Move to another item and back and it is still running, or still showing the result. The list row shows Replacing, then Replaced.
  • The done state shows Was and Now, refreshes every field, and offers Undo, Replace again, Done.
  • Undo survives a refresh because the before-snapshot is saved on the item. That is an open question below.
  • Errors are a card with Try again. The item is untouched until the backend succeeds.

Proposal A: one shot, fixed

Same shape as today with the bugs removed. Cheapest to build. "Replace again" costs another 20 to 40 seconds each time.

Proposal B: pick from three recommended

One AI call drafts three complete candidates (same wait, roughly double the output tokens). Nothing is written until you pick one, and "try another" is instant. The team's real loop is "not that one, again", and this makes that loop free.

For the build

What it takes

  • Frontend. Lift the replace state out of the panel into the calendar page's item-actions hook, keyed by item id. New ReplaceCard component at the top of the panel. The draft hook resets on a replace counter, not on the meta description. Pass the read-only flag through.
  • Backend. Gate per-item replace the same way full regeneration is gated (sample projects, mid-review lock). Stream the regenerate endpoint the way bulk meta generation already streams. Proposal B adds a candidates call that returns three drafts and an apply call that writes the chosen one.
  • Tests. A frontend test for the panel refresh after replace, since none exists today, and backend tests for the new gates.
